# Routing Algorithm Test Harness and Results Website

Several people each write a routing algorithm. This repo provides the specification, a graph builder, a test harness that runs and independently validates every algorithm on the same instances, and a static website that shows results and routes on a map. `PROJECT_BRIEF.md` is the source of truth.

**Problem:** from a depot, depart at a given time and return within a period, visiting as many distinct customers as possible, each within its one time window (4 slots over 06:00-24:00). Ties go to shorter distance.

## Layout

| Path | Contents |
|---|---|
| `PROJECT_BRIEF.md` | Full brief (wins over everything else) |
| `data/` | GeoNames Malaysia dataset (`MY.txt`), field definitions and provenance |
| `docs/` | Course brief PDF; `docs/ALGORITHM_SPEC.md`, the specification for algorithm authors |
| `harness/` | Python harness (graph builder, validator, runner, aggregator) |
| `tests/` | Test suite |
| `algorithms/` | One folder per algorithm (`algorithm.json` plus the program); `nearest-neighbour` is the baseline |
| `site/` | The results website: `serve.py`, `index.html`, `css/`, `js/` (plain HTML/JS, no build step) |
| `instances/`, `results/` | Generated by the harness, ignored by version control |

Harness: Python 3 (standard library only). Website: plain HTML/JS.

## Quick start: run the evaluation and open the website

You need Python 3 and git (nothing to install; the harness and the server use only the standard library) and a web browser. An internet connection is optional: it is only used for the map tiles, and the map falls back to a plain drawing without it.

```
git clone https://github.com/akwsy/TSP_algo.git
cd TSP_algo
python3 start.py
```

`start.py` does two things in order:

1. **Runs the evaluation.** It builds the problem instances, runs every algorithm in `algorithms/` on the same instances, checks each answer independently, and writes the results into `results/`. **Evaluation is incremental:** each algorithm is evaluated only once. A saved run is reused when the algorithm's code (a hash of every file in its folder, including `algorithm.json` and so its time limit), the instance and the settings are unchanged, so running `start.py` again evaluates nothing new and says so ("Reusing 210 saved runs, running 0 new"). Editing one algorithm re-evaluates only that algorithm; adding one evaluates only the new one; extra sizes or instances run only the missing pairs. The first full default run (7 sizes from 5 to 100 customers, 30 instances each) takes about 10 seconds with the baseline algorithm.

   Saved data lives in `results/` (one file per run, `index.json`, the full-run files in `results/sessions/` with their own `sessions-index.json`, and `aggregates-scaling.json`) and `instances/` (all ignored by version control). Delete those folders to start completely fresh. Runtimes are saved with the run, so re-evaluating an algorithm (`--rerun`) refreshes its runtimes; reused runs keep the runtimes measured when they ran. Runs saved by an older version of the harness carry no fingerprint and are re-evaluated once.
   `start.py` also runs the second view, **until every place is visited**, on the first 10 examples of each size (see "Full-run evaluation" below). It is saved and reused in the same way, and takes much longer than the first-day run the first time.
2. **Starts the website** at http://127.0.0.1:8000/ and opens it in your browser. Press Ctrl+C in the terminal to stop it.

Useful options:

```
python3 start.py --sizes 5 10 --instances 3       # a quick small run first
python3 start.py --skip-run                       # just open the site on results you already have
python3 start.py --full-run-instances 3           # examples per size run until every place is visited (default 10, 0 to skip)
python3 start.py --force                          # re-evaluate everything (both views), ignoring saved runs
python3 start.py --rerun nearest-neighbour        # re-evaluate only the named algorithms in both views (refreshes their runtimes)
python3 start.py --port 8001                      # if port 8000 is busy
python3 start.py --no-browser                     # do not open a browser window
```

**What you see on the website.** A toggle in the page header switches between **First day only** (30 examples per size, one working day) and **Until every place is visited** (10 examples per size, one day after another). Your choice is remembered and applies to Overview, Scaling, Instance and Route detail. It is a two-option choice you reach with Tab and change with the arrow keys (or click). Top navigation:

- **Overview:** every algorithm side by side with a ranking, its declared complexity, and failure counts. First day only: most places visited, then shortest distance. Until every place is visited: fewest mean working hours, then shorter distance; algorithms that finished every example come first, the others are listed below as "ranked below: N instances did not finish", with averages over the examples that finished. Pick the number of customers from the dropdown.
- **Scaling:** First day only: charts of visits, distance, time and runtime against the number of customers, and how measured runtime and work grow compared with the declared complexity (this growth plot appears only in this view). Until every place is visited: working hours, days needed, total distance and total compute time against the number of customers, with spread.
- **Instance:** one problem at a time, showing every algorithm's route on the map for comparison (side by side or overlaid). In the full-run view a **Day** selector steps through day 1, day 2 and so on; places done on earlier days are shown as done.
- **Route detail:** one algorithm's run on one example, with the map and a step-by-step table. Choose the algorithm, the example and the number of places from the dropdowns. In the full-run view a **Day** selector shows that day's route and schedule table.
- **History:** results grouped by algorithm version (git commit), to compare an algorithm before and after a change; full runs are included.
- **Failures:** runs that were invalid, crashed or timed out, with the reason; in the full run, instances that were stopped, with the day, the plain reason and the progress so far.

**To evaluate your own algorithm:** put it in `algorithms/<your-id>/` following `docs/ALGORITHM_SPEC.md`, commit it, and run `python3 start.py` again. It appears next to the baseline on every page. The same document contains a checklist and instructions for AI coding agents.

**To look at the website without running anything:** this shows the committed sample results, including some deliberately broken algorithms.

```
python3 site/serve.py --results tests/fixtures/sample-results --algorithms tests/fixtures/sample-algorithms --instances tests/fixtures/sample-instances
```

The separate commands behind `start.py` are described in the next sections.

## Run the experiment

```
python3 -m harness.experiment scaling                                   # sizes 5,10,15,20,30,50,100, 30 instances each
python3 -m harness.experiment scaling --sizes 5 10 15 --instances 5     # a quick run
```

This is incremental, with the same `--force` and `--rerun ID [ID ...]` options as `start.py`: it builds the instances into `instances/`, runs every algorithm in `algorithms/` on them (skipping pairs already saved for the same code and instance), validates each answer independently, and writes one JSON record per run plus `index.json` and `aggregates-scaling.json` into `results/`. Use `--results-dir`, `--instances-dir` and `--algorithms-dir` to write elsewhere.

The experiment also runs each algorithm on the first 10 instances of each size **until every place is visited**: day 1 is the normal first-day run, and each later day gives the algorithm only the places still unvisited (leave 06:00, back by 24:00). One file per algorithm and instance is written to `results/sessions/` (layout documented in `harness/session.py`) with the days, the total working hours (travelling plus waiting, nights excluded, last day only until the last place is served) and the total distance and compute time. Use `--full-run-instances N` (default 10, 0 to skip) to change how many instances get this run. `--force` and `--rerun` re-evaluate the full runs too, and the run is capped at 30 days.

## Experiments

Each experiment varies ONE instance parameter and keeps everything else at the defaults unless stated. Every algorithm runs on identical instances (seeds 1 to N for each value). They are defined in one place, `harness/experiments.py`.

| Name | Varies | Values | Fixed | Instances per value |
|---|---|---|---|---|
| `scaling` | customers | 5, 10, 15, 20, 30, 50, 100 | defaults | 30 |
| `time-budget` | travel period (minutes from the 06:00 departure) | 240, 480, 720, 960, 1080 | 30 customers | 30 |
| `speed` | speed (km/h) | 20, 30, 40, 60, 80 | 30 customers | 30 |
| `window-alignment` | departure minute of a 6-hour period | 360, 540, 720, 900, 1080 | 30 customers, period 360 | 30 |
| `spread` | selection radius around the depot (km) | 25, 50, 100, 150, 250 | 20 customers | 30 |
| `stress` | customers | 100, 150, 200, 300 | defaults | 10 |

`spread` uses 20 customers because the dataset has 544 candidate places within 25 km of Kuala Lumpur (and 1154, 3090, 5212, 8423 within 50, 100, 150, 250 km), so every radius can supply them. Instance ids gain `-rad<N>` when the radius is not the default 150 (like `-dep`, `-per`, `-spd`).

```
python3 -m harness.experiment --list                       # print the experiments
python3 -m harness.experiment suite                        # run all six in order
python3 -m harness.experiment time-budget                  # run one
python3 -m harness.experiment speed --values 20 40 --instances 5     # a quick slice
python3 -m harness.experiment spread --fixed customers=10  # change a fixed parameter
python3 start.py --suite                                   # the suite, then the website
```

`--values` replaces the sweep values (`--sizes` is the same for the customers experiments `scaling` and `stress`), `--instances` the instances per value, `--fixed NAME=VALUE ...` the fixed parameters. Progress is one line per sweep value. Only customers experiments can run the "until every place is visited" view (default: 10 instances for `scaling`, none for `stress`; `--full-run-instances N`).

Every run record and `index.json` entry carries `experiment`, `sweepParam` and `sweepValue` (for `scaling`, `customers` and the number of customers). Each experiment writes `results/aggregates-<name>.json`: the usual `groups` (now with `sweepParam` and `sweepValue`; `numCustomers` is kept) and `sweepValues`, plus `pairs`, a paired comparison of every pair of algorithms (a before b alphabetically) at each sweep value over the instances where both runs are valid (counts of wins and ties by the scoring rule, mean visit difference with a deterministic bootstrap 95% interval, route overlap, the largest gaps; definitions in `pairwise` in `harness/aggregate.py`). The suite also writes `results/suite.json`, listing each experiment with its description, parameter, values, instances, algorithms, aggregates file and timestamp. The algorithms here are deterministic, so the `pairs` are identical on every run; measured runtimes naturally differ.

## Full-run evaluation

Design decisions for the "until every place is visited" view (confirmed with the owner except where noted):

- **Same experiment.** It is part of `scaling`, on seeds 1 to 10 of each size (a subset of the 30 first-day instances), with the same sizes. `--full-run-instances N` changes the count (default 10, 0 to skip, never more than `--instances`).
- **Day loop.** Day 1 is the first-day run (reused from its saved record when present). Each later day the algorithm gets only the unvisited places and the depot (id 0, customers renumbered 1..k in original order), the same seed, departure 06:00, deadline 24:00 and the same four slot windows. Every day is checked by the independent validator.
- **Working hours.** Per day, the time from the 06:00 departure until back at the depot (travelling plus waiting); nights and idle time at the depot excluded. The last day counts only until the last place is served. The total is the sum.
- **Caps.** At most 30 days (proposed by the assistant, accepted by the owner). A session stops, unfinished, when a day visits no new places, at the 30-day cap, or on any failure (crash, invalid route, unreadable output, timeout with no answer). Its partial figures are never used as a finishing time and never enter averages or rankings.
- **Saving.** One file per algorithm and instance in `results/sessions/`, indexed by `results/sessions-index.json`, reused while the algorithm folder, instance, time limit and settings are unchanged, and the harness's session rules (`SESSION_FORMAT_VERSION` in `harness/session.py`) and day limit (30, or the advanced option `--max-days N`) are the same; a change to either runs the session again. `--force` and `--rerun` apply to both views. Runs saved before this feature have no full-run data until evaluated.

## Run the tests

```
python3 -m unittest discover -s tests
```

`tests/test_site_pages.py` loads every website view in headless Google Chrome and fails on any console error, uncaught exception, stray `false`/`null`/`[object` text or horizontal page scroll. It skips when `node` or Chrome is missing. For screenshots at desktop and phone widths in light and dark mode: `node tests/site_smoke.mjs http://127.0.0.1:PORT --matrix --shots DIR`. The script also works against real results (`python3 site/serve.py --results results ...`): checks about content that depends on the data (stopped sessions on Failures, the "ranked below" label, the "Not plotted" note, how many days the Day selector offers) are derived from the served data and apply only when the data contains what they check for.

## Run the website

```
python3 site/serve.py                      # reads ./results and ./algorithms, http://127.0.0.1:8000/
python3 site/serve.py --results tests/fixtures/sample-results --algorithms tests/fixtures/sample-algorithms --instances tests/fixtures/sample-instances
```

`results/` is not committed; create it with `python3 -m harness.experiment scaling`. The second command shows the committed sample results (including failed runs). No build step. It works offline except for the optional map library and tiles (see the last section). Pages live in `site/js/pages/` and are listed in `site/js/pages/index.js` (see the comment there to add one). Data logic that is tested lives in `site/js/lib/model.js` (tests need `node`; they skip without it).

## Unconfirmed assumptions (brief section 12)

1. "6 a.m. to 12 a.m." means 06:00 to midnight (18 h), four 4.5 h slots.
2. Default selection: depot Kuala Lumpur, customers a seeded sample of populated places (class `P`) within 150 km, without replacement.
3. Defaults: departure 06:00, period 1080 min (06:00 to midnight), speed 40 km/h.
4. Reported metrics: distance (km), travel time, total time (travel plus waiting).
5. Experiment sizes 5, 10, 15, 20, 30, 50, 100 with 30 instances each are proposals; the full run uses the first 10 of each.
6. Algorithms are language-agnostic CLI programs (JSON over stdin/stdout); harness in Python, site in plain HTML/JS.
7. No algorithms are carried over from the old repo (history only).

## Deviations decided during the build

- The nearest neighbour algorithm is a real, labelled baseline (`algorithms/nearest-neighbour`). The always-empty example algorithm from brief section 7 was dropped. The broken algorithms used to test failure handling live only in `tests/fixtures/`.
- Work happened directly on `main` by the owner's choice, with no feature branch or pull request.
- `timeLimitSeconds` is declared in `algorithm.json` and added to the instance sent to the algorithm by the runner at run time; it is not part of the stored instance file.
- The map loads Leaflet 1.9.4 from cdnjs (pinned, with subresource integrity) and OpenStreetMap tiles; offline or when Leaflet is blocked, the page falls back to a plain projected map with the same routes. Everything else works offline.
